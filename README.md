# Astro Health Monitor

Offline-first PWA for monitoring astronaut health: it works without internet (IndexedDB) and syncs with Supabase when a connection is available.

Built for NASA Space Apps 2026. UI in Spanish and English; code, variables and comments in English.

## Stack

- [Vite](https://vite.dev/) + [React](https://react.dev/) (JavaScript, ESLint)
- [vite-plugin-pwa](https://vite-pwa-org.netlify.app/) – service worker, precache, web manifest
- [Dexie](https://dexie.org/) (+ `dexie-react-hooks`) – IndexedDB local database
- [Supabase](https://supabase.com/) (`@supabase/supabase-js`) – cloud sync
- [React Router](https://reactrouter.com/) – routing
- [i18next](https://www.i18next.com/) + `react-i18next` – ES / EN
- [Recharts](https://recharts.org/) – charts
- [three.js](https://threejs.org/) – interactive 3D astronaut (glTF model with a procedural fallback)

## Roles and flow

Online, users can sign in with Google from `/login`. Supabase Auth maps each linked account to exactly one profile. Offline, the demo uses a 4-digit PIN checked on the device (SHA-256). Demo PINs: ground flight surgeon `9999`; astronauts One `1111`, Two `2222` (ISS medical officer), Three `3333`, Four `4444`, Five `5555` (Mars medical officer).

**Astronaut**

1. `/` Home: blood pressure, SpO₂ and heart rate cards, the five body systems with their traffic light, the 3D astronaut (click a zone or a system to select it) and the clinical card of the selected system (NASA HRP hazard and risk).
2. `/vitals`, `/system/:code`, `/alerts`, `/checkin`, `/sensors`, `/comms`: live charts, system history, alerts with the recommended action, daily self-report, simulator / Bluetooth sensor, and notes from the flight surgeon.

**Ground flight surgeon**

1. `/` Control center: every mission at once (astronauts, critical, warning, unattended alerts, unread notes), the crew members that need attention first, mission shortcuts and recent notes.
2. `/missions` → `/missions/:id`: pick a mission (ISS, Mars transit) and see its crew. The signal delay of the mission is shown next to its name.
3. `/crew` → `/crew/:userId`: all five demo astronauts by default, with a mission filter, then the detail of one astronaut with a 3D body view, trends, thresholds, alerts and notes.
4. **Note ↔ alert**: "Enviar nota" from an alert pre-fills the note and links it (`alertId`). When the astronaut marks the note as read in `/comms`, the alert becomes attended for the surgeon.

The crew medical officer (an astronaut) sees the crew table of their own mission in read-only mode.

**Theme**: light by default with a dark toggle in the top bar (`src/theme/theme.js`, `<html data-theme>`). Every color comes from the tokens in `src/index.css`; charts and the 3D stage pick their palette from `useTheme()`.

## Getting started

```bash
npm install
npm run dev
```

Other scripts:

```bash
npm run lint      # ESLint
npm run build     # production build (generates the service worker)
npm run preview   # serve the production build (use this to test the PWA / offline mode)
```

The service worker is only generated by `npm run build`; it is not active in `npm run dev`.

## Environment variables

Supabase is optional: without it the app runs in offline-only mode (a warning is logged to the console).

1. Copy `.env.example` to `.env`.
2. Fill in the values from the Supabase dashboard (Project Settings > API):

```
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=
```

`.env` is git-ignored. Never commit it.

## Folder structure

```
public/               PWA icons (icon.svg, pwa-192x192.png, pwa-512x512.png)
src/
  pages/              One file per screen (Login, Home, Vitals, SystemDetail, Alerts,
                      Checkin, Sensors, Comms, Crew, CrewMember)
    home/             Astronaut dashboard pieces, ControlCenter (surgeon home), MissionOverview, ModelStage
    missions/         Mission list and the current-mission store
    crew/             Crew table, member detail, alerts, notes, body view, chart themes
  components/         Shared UI (Layout, ConnectionStatus, AstronautModel3D, ThemeToggle, icons)
  theme/theme.js      Light / dark theme store (useTheme)
  data/
    simulator.js      Simulated vital signs
    demoCrew.js       Starting history of the demo astronauts
    adapters/         Dataset adapters (dataset rows -> Reading)
    seed/             JSON loaded into IndexedDB on first run (single source of truth, see below)
  db/db.js            Dexie schema (AstroHealthDB) + seedIfEmpty()
  rules/              engine.js (thresholds -> alerts), baseline.js (personal baseline)
  sync/               Supabase client + sync queue (push pending rows, pull notes)
  bluetooth/          Web Bluetooth heart rate sensor
  auth/               PIN + local session
  i18n/               i18next setup, es.json, en.json
  models/reading.js   Reading type + createReading()
  App.jsx             Routes
  main.jsx            Entry point
```

Conventions:

- All IDs are string UUIDs (`crypto.randomUUID()`), never auto-incremented.
- Create readings only through `createReading()` in `src/models/reading.js`.
- Every user-facing string goes through i18n: add the key to both `es.json` and `en.json`.
- Changing the Dexie schema means adding a new `db.version(n)`; do not edit an existing version.
- `supabase` can be `null`; always check before using it.

## Git workflow

- `main` must always build. Do not commit directly to it.
- One branch per person and task, named `name/task` (e.g. `ana/vitals-screen`).
- Open a Pull Request into `main`; run `npm run lint` and `npm run build` before asking for review.
- Pull `main` often to keep conflicts small:

```bash
git checkout main
git pull
git checkout -b name/task
```

## Clinical thresholds

The 18 demo rules in `src/data/seed/thresholds.json` carry a `source` and a `validated` flag. Two rules are marked validated and cite published references for bone-density loss and radiation exposure. The radiation caution margin is an app convention. The other 16 rules need source verification before clinical use.

Skin temperature uses each astronaut's personal baseline. Mood and stress use the app's 1–5 check-in scale. The ground flight surgeon can adjust thresholds per astronaut. Demo scenarios use simulated readings.

## Supabase database

`supabase/setup_final.sql` initializes a fresh demo database (Supabase > SQL Editor). It drops and recreates the app tables, deleting existing demo data and profile links. Use the upgrade script below for an existing project.

It is generated, do not edit it by hand:

- Data: `src/data/seed/*.json` (the same files the client loads into IndexedDB).
- Schema: `scripts/schema.sql`.

```bash
npm run gen:sql   # regenerates supabase/setup_final.sql
```

Upgrading an existing database without dropping it: run `supabase/upgrade_missions_alert_id.sql` in the SQL Editor (adds the missions columns, `messages.alert_id`, the Mars demo mission and astronauts Four and Five; safe to run more than once). The `alter table ... add column if not exists` lines in `scripts/schema.sql` are the same changes.

### Sync

Vite reads the two Supabase variables from `.env` or `.env.local` in the repository root. Restart `npm run dev` after changing them. For a Vercel build, set the same variables in the project settings and redeploy.

1. Configure a Google OAuth web client with the Supabase callback URL and enable Google in **Authentication → Sign In / Providers**. For a demo using a Google OAuth app in testing mode, add the team's Google accounts as test users.
2. In Supabase **Authentication → URL Configuration**, set the production site URL and allow the app's `/login` redirect URL. Also allow `/comms` if testing Google sign-in from Communications after an offline PIN login.
3. Open the app in separate browser profiles or devices. On the login page, choose **Continue with Google** using the assigned Google account. First sign-in creates a Supabase Auth user. A linked account opens the assigned profile without a PIN.
4. In **Authentication → Users**, verify the email and Google identity for each account. Set each assigned profile's `public.users.auth_user_id` to that account's UID. `supabase/link_demo_profiles.sql` covers all six demo profiles and preserves existing links. Run it only for profiles that still need a link.
5. Generate a reading and an alert as Astronaut One, then sync. Sync as the flight surgeon and check the reading under **Crew → Astronaut One**. Send a note from the synced alert and sync again.
6. As Astronaut One, sync and mark the incoming note as read, then sync again. Sync as the surgeon and verify the alert is shown as attended.

The queue also runs every 30 seconds and on reconnect. The header and Communications show pending records for the active profile. The queue uploads that profile's readings, alerts, check-ins with symptoms, and notes. Both roles receive their own conversations. The ground flight surgeon and onboard medical officers download the crew readings and alerts allowed by Row Level Security and can view cached records offline.
### Demo verification

- **Sync in two devices.** As Astronaut One, start the Hypoxia simulator in Sensors until a critical alert appears, then stop it and sync in Communications. As the ground flight surgeon, sync, open that alert in Crew and send a note. Sync, read the note on the astronaut device, and sync both devices again. Verify the alert shows as attended on the surgeon device.
- **Offline reload.** Load the deployed app online and wait for the service worker to install. Sign out, switch the browser to offline mode, reload and enter using the demo PIN. Check that the 3D view loads. Generate a simulator reading, verify it is pending, then reconnect and sign in with Google to sync it.
- **Bluetooth.** On a separate Android phone, configure nRF Connect to advertise the connectable Heart Rate service (0x180D). Open AstroSalud over HTTPS in Chrome and pair it from Sensors. Verify that bpm updates. The phone emits simulated pulse readings. Repeat with a physical heart-rate monitor to verify hardware compatibility.
